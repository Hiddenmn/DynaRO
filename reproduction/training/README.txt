DynaRO local training component
===============================

This is a new path-independent driver for the recorded training configurations,
not a replacement for the original experimental outputs. It uses the prepared
model core, inputs and evaluation component (for the unchanged trajectory
reader). No private project directory or historical experiment script is
required at runtime. This local candidate has not been published or licensed.

Two distinct studies
--------------------
mixed_horizon: static_front, dynaro, coarse_front, fno and rtu; three seeds each.
Each of 800 paired schedule IDs appears at 25 and 50 steps. Every optimizer
update uses two IDs, each at both horizons (four pair gradients). Full-chain
gradients are retained. The only eligible checkpoint is final update 400.

learning_rule_25: response_weight_0, fixed_weight_50, du_cosine_gate and
state_prioritized have three seeds; pcgrad has seed 20260811 only. All use the
static-front model, 800 pairs at 25 steps and five-step gradient windows. Every
update accumulates four pairs / twenty windows; final update 200 is selected.
This study uses t/25, whereas the mixed-horizon study uses t/(t+25).

Defaults are read-only
----------------------
  python train.py --core CORE --inputs INPUTS --evaluation EVALUATION \
    --model-key mixed_horizon/dynaro/20260811

The command checks the component files and protocol without opening trajectory
arrays, loading initial states, constructing a model, or allocating a GPU. Add
--train25 TRAIN25_DIRECTORY --train50 TRAIN50_DIRECTORY to check file presence.
For learning_rule_25 omit --train50. Original trajectory files are accepted by
default. A complete batch generated by the input component requires
--data-kind regenerated and its batch directory; generated and original file
identities remain distinct. DEV and TEST are never read by this training entry.

Training is a separate, explicit action
---------------------------------------
Actual execution additionally requires --execute --output NEW_DIRECTORY and a
positive --max-seconds value, a compatible Linux/CUDA runtime, and an available
RTX 4090. A time limit is checked at complete optimizer-update boundaries, not
during an individual pair. A STOP_REQUESTED file in the output directory has
the same effect. This is a soft limit, not a guarantee of maximum wall time.
No CPU training fallback, server start, download, upload or evaluation occurs.

The driver verifies the recorded initial-parameter and shuffled-pair hashes
before opening training arrays. Coarse-front seeds 20260812/20260813 restore
their exact pre-update state and CPU RNG state from the included initialization
files; these are not trained weights. FNO/RTU use the recorded server wrappers
with full transition checkpointing and without nested block checkpointing.
The expected hashes must not be replaced to make another environment pass.

Use --resume with the same component files, inputs and output only for this
driver's incomplete runs. Recovery state includes model, AdamW, CPU/CUDA RNG,
completed updates and context. The latest checkpoint is a recovery artifact,
not a selected result. retrained_final.pt contains only the final model tensors;
summary.json identifies it as a new retraining output, not a published result.
It must not overwrite or be presented as any of the frozen original weights.
The separate evaluation entry currently accepts the original frozen weights;
evaluation of a newly retrained checkpoint needs an explicit separate route.

What is and is not preserved
----------------------------
The original gradient kernels, server model wrappers, gradient combination
rules, accumulation order/scales, pair orders, starting states, optimizer and
checkpoint-selection rules are preserved. Source definitions are recorded in
manifest.json. The driver adds portable paths, explicit run controls and new
recovery files. Historical post-training bookkeeping and comparisons to other
TRAIN runs do not determine updates and are not copied into this driver.

Local code tests are not a full CUDA training reproduction. In particular, the
available Windows/CPU runtime does not reproduce the recorded FNO/RTU initial
hashes; the strict guard deliberately stops those configurations there. The
original frozen models remain available in the separate weights component.
No complete research training run has been executed with this new driver.
